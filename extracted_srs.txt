1. Introduction
1.1 Purpose
This Software Requirements Specification (SRS) defines the functional and non-functional
requirements, constraints, and design models for UniOne, a mobile-first platform for student
collaboration, community networking and career discovery at Superior University. It is the agreed
reference for developers, testers, supervisors and stakeholders, and it is derived from the project's
technology-stack research and master blueprint.
1.2 Project Introduction
Students today split their academic and professional lives across WhatsApp and Discord groups
(unstructured and short-lived), Facebook Groups (weak moderation, no professional identity) and
LinkedIn (costly job posts, no peer-collaboration tools). UniOne unifies these in a single ecosystem
built on verified university identity. Its core ideas are:
 Identity drives permissions: rights such as posting internships are tied to verified roles.
 Low friction for discovery, strict control for risk: anyone verified can browse; high-stakes
actions are reviewed.
 Durable knowledge over fleeting chat: threaded discussions with New/Best sorting; real-time
chat is reserved for project teams and private groups.
 Structured opportunities: job, internship and collaboration posts are schema-bound objects
that auto-expire (14 days).
1.3 Scope
In scope (MVP):
 University-email verification, onboarding and academic profiles.
 Seven community types: Open Interest, University, Academic/Study, Project, Career/Internship,
Official Announcements, Private Collaboration Group.
 Threaded discussions, voting, New/Best sorting, search and notifications.
 Structured collaboration requests, project workspaces with real-time team chat.
 Verified-organization internship/job listings with pre-publication review and applications.
 Direct messages with a Message Request queue, block/report tools.
 Reason-coded moderation, appeals, immutable audit logs, and a web admin dashboard.
 Android and iOS app built in Flutter; NestJS backend; PostgreSQL; Socket.IO real-time.
Out of scope (deferred to Phase 2/3): Industry Network, Employer Talent Channels and
Mentorship communities, voice/video (LiveKit), AI matching and semantic search, end-to-end
encryption, microservices/Kafka/Kubernetes, multi-region deployment.

2. Overall Description
2.1 Product Perspective
UniOne is a new, self-contained system made of three deployable parts from one monorepo: a
Flutter mobile client, a NestJS modular monolith (REST API, Socket.IO gateway and BullMQ workers)
and a React admin dashboard. Data lives in PostgreSQL (source of truth), Valkey/Redis (presence,
pub/sub, queues) and Cloudflare R2 (media). The mobile app treats its local Drift database as the
single source of truth for the UI; REST and WebSocket events reconcile into it, which gives offline
support and reliable chat.
 Figure 2.1 - High-level system architecture
2.2 Product Functions (Summary)
 Authentication, university verification and onboarding
 Profiles and privacy controls
 Communities (7 types), join gates and roles
 Discussion feed with threaded comments and voting
 Collaboration requests and private project workspaces
 Real-time chat and message requests
 Verified opportunity listings and applications
 Notifications (in-app and push)
 Search (people, communities, posts)
 Reporting, moderation, appeals and audit logs
 Administration dashboard

2.4 Operating Environment
 Mobile: Android (API 24+) and iOS (15+), built with Flutter (current stable).
 Admin dashboard: current Chrome, Edge, Firefox, Safari (desktop).
 Server: Node.js 24 LTS containers (Railway or ECS Fargate), managed PostgreSQL, Valkey/Redis,
Cloudflare R2/CDN.
2.5 Design and Implementation Constraints (summary)
Flutter/Dart is a fixed decision for mobile. Backend uses TypeScript/NestJS. OpenAPI 3.1 is the
contract. Student-budget hosting (about USD 35-60/month at pilot) restricts the design to managed
services and a monolith. See Section 6 for the full list.
2.6 Assumptions and Dependencies
 Students hold active university email addresses on a known domain (e.g. @superior.edu.pk).
 Third-party services (FCM, APNs, SES, Cloudflare, managed Postgres) remain available at the
assumed pricing.
 University leadership will nominate announcers and career-office accounts.
 Planning load: 100,000 registered users, about 20% daily active, about 1,000 peak concurrent
connections.

8. Use Case Specifications
UC-01 Register and Verify University Email
Primary actor
Student
Preconditions
App installed; user has a university email.
Main flow
1. User enters email and password. 2. System validates domain, creates a pending account
and sends OTP. 3. User enters OTP. 4. System sets status VERIFIED and enrolls the user in the
institutional community. 5. User completes onboarding.
Alternative flows
A1: Domain not allowed - show error. A2: OTP expired or wrong - allow retry/resend (max 5
attempts).
Postconditions
Verified account exists; institutional community joined; starter feed shown.
UC-02 Join Community
Primary actor
Student
Preconditions
User is verified and logged in.
Main flow
1. User opens the community preview. 2. System shows rules, member count and join mode. 3.
User taps Join. 4. System adds the user to the roster.
Alternative flows
A1: Request Access - user answers up to 3 screening questions; moderator approves. A2:
Invite-Only - join disabled.
Postconditions
User is a member (or pending request created).
UC-03 Post Discussion with Threaded Replies
Primary actor
Member
Preconditions
User is a member with posting rights.
Main flow
1. User opens the composer and selects Discussion. 2. User enters title, body, optional
code/image. 3. System validates and publishes. 4. Members reply and vote; the feed sorts by
New or Best.
Alternative flows
A1: Community requires post approval - post enters review queue. A2: Offline - post is stored in
the outbox and sent later.
Postconditions
Post visible in the community and in followers' feeds.
UC-04 Send Direct Message / Message Request
Primary actor
Student
Preconditions
Sender and recipient are verified.
Main flow
1. Sender writes a message. 2. App stores it in the outbox and shows it as pending. 3. Server
persists and acknowledges. 4. If the sender is a non-connection, it arrives in the recipient's
Message Requests. 5. Recipient accepts.
Alternative flows
A1: Recipient blocks - future messages rejected. A2: Connection lost - client retries with the
same idempotency key.
Postconditions
Message stored once with a sequence number; delivery state updated.
